# Windows 직접 실행 검사 결과

2026년 11월 17일(한국 시간), 승인된 `codex/windows-verify-20261117` 브랜치에서 Windows 네이티브 검증을 진행했다. 대상 코드는 `17791fccfd28ff5675d00a3e06dce6c05a45de63`다. [최종 실행 44021179246](https://github.com/P-JSL/myapps/actions/runs/44021179246)에서 아래 40개 검사가 모두 통과했다.

실행 환경은 GitHub `windows-2025`의 Windows Server 2025 x64다. 데스크톱 ZIP을 `Windows 앱 실행 검사\MyVideoApp`에 풀고 내장 Python 3.13.17·PySide6 6.12.0·yt-dlp 2026.10.21·curl-cffi 0.16.3·FFmpeg를 사용했다. 확장은 실제 Chromium에 설치했다.

## 수정한 문제

| 문제 | 원인과 수정 |
| --- | --- |
| 일반 CDN의 직접 HLS 주소 거부 | yt-dlp Generic이 `manifest_url` 없이 자기 URL을 반환하는 미디어 재생목록도 실제 HLS 본문을 확인해 허용한다. 암호화·라이브·오류 HTML 거부는 유지한다. |
| GUI 다운로드 준비·취소 지연 | PySide/Shiboken의 소스 검사 훅이 첫 yt-dlp import에 개입했다. 버전과 경로를 확인한 내장 다운로더를 Qt보다 먼저 준비한다. 수정 후 Windows 준비 단계가 약 0.4초에 끝나고 HLS 저장이 완료됐다. |
| 한글 설치 경로의 MissAV TLS 실패 | curl-cffi의 Windows ANSI 파일명 변환과 프록시 요청의 내장 certifi 경로가 충돌했다. Python으로 같은 인증서 내용을 읽고 libcurl의 CA blob 복사 옵션으로 전달한다. TLS 검증과 스레드별 핸들을 유지한다. 신뢰하지 않는 인증서가 거부되는 회귀 검사도 추가했다. |
| HLS 취소 후 재시도 시 파일 이름 변경 실패 | 예외로 중단된 yt-dlp 조각 다운로드가 열린 파일을 보관했다. 작업이 종료된 뒤 해당 작업 폴더의 스트림과 예외 참조를 정리해 Windows 파일 잠금을 해제한다. |
| MissAV CDN 요청의 원본 정보 | 페이지의 Referrer 정책과 관계없이 승인된 영상의 요청에 원본 사이트 주소만 전달한다. 페이지 경로·쿼리를 보내지 않으며, `no-referrer` 페이지를 사용한 설치 확장 검사도 통과했다. |

이전 검사 코드의 CP1252 로그 출력, 지원하지 않는 EXE 인자 전달, 너무 엄격한 창 제목 비교도 수정했다. 이는 검사 도구의 문제였으며, 제품 런처의 인자 무시·경로 검증 정책은 유지했다. 다운로드 제한 시간을 늘려 통과시키지 않았다.

엔진, 분리된 메타데이터 작업기, Chrome API는 교체하지 않았다. 확장에서는 콘텐츠 스크립트·서비스 워커·오프스크린 문서·OPFS·FFmpeg WASM·다운로드 API를 사용하고, 저장 폴더 최초 설정도 실제 UI로 확인했다. 저장 파일은 Chrome의 저장 완료와 파일 존재, FFprobe의 영상·음성 트랙, 디코딩한 영상 프레임의 원본 해시 일치를 확인했다.

데스크톱의 취소·재시도는 작업 ID를 유지하고, 확장은 기존 구현대로 새 시도를 만든다. 보안 확인 창은 실제 ‘나중에 확인’ 버튼으로 닫으며, 위험 결과를 승인하거나 백신 검사를 성공한 것으로 바꾸지 않는다.

## 결과와 제한

최종 결과: 위 40개 검사 모두 통과. Windows GUI 7개, MissAV 특화 확장 6개, 확장 2종 UI 각 3개의 검사 JSON에서 실패·오류 배열이 모두 비어 있음을 확인했다.

위 40개 회귀 검사의 영상은 저장소가 소유한 짧은 H.264/AAC 샘플이다. 데스크톱의 테스트용 HTTPS CONNECT 서버는 허용된 가상 호스트를 로컬 TLS 서버에만 연결하고 인터넷으로 전달하지 않는다. MissAV 특화 확장 검사는 테스트 응답을 제공하고, 두 확장의 일반 다운로드 UI 검사는 실제 루프백 HTTP 서버를 사용한다.

### 제공된 실제 영상의 전체 다운로드

[실제 URL 실행 44021176779](https://github.com/P-JSL/myapps/actions/runs/44021176779)도 같은 코드로 성공했다. Windows에서 브라우저 창을 열고 MissAV 포함 확장을 새로 빌드해 설치했으며, 실제 사이트 응답과 Chrome API를 교체하지 않았다.

검사한 주소는 사용자가 제공한 `surrit.com/00b3d04e-11d2-4b39-b591-ea2af84f8756/1080p/video.m3u8`다.

| --- | --- |
| HLS 전체 구간 | 921개 |
| CDN 응답 | 성공 923개, 실패 0개: 재생목록 요청 2개와 영상 구간 921개 |
| 전체 재생목록 길이 | 3,682.933333초 |
| 저장 파일 길이 | 3,682.965333초, 약 61분 23초 |
| 저장 파일 크기 | 1,974,360,037바이트, 약 1.97GB |
| 영상·음성 | H.264 1920×1080, AAC |
| 저장 확인 | Chrome 저장 완료와 실제 파일 존재 확인 |
| 디코딩 확인 | 처음과 끝에서 각각 영상·음성 1초 디코딩 통과 |

원본 `hame-044` 페이지는 Windows에서 HTTP 200으로 열렸다. 페이지를 열기만 한 상태에서는 제공된 UUID의 자동 감지를 확인하지 못했다. 검사 과정에서 해당 페이지 안에서 제공된 m3u8를 실제 요청했고, 확장이 그 네트워크 요청을 감지한 다음 실제 주소 입력 폼으로 전체 파일을 받았다. 따라서 이 결과는 원본 탭에 해당 미디어가 감지된 상태에서의 직접 m3u8 다운로드 검증이다. 원본 페이지 자동 재생·자동 감지까지 성공했다고 확대하지 않는다.

파일은 저장됐으나 로컬 백신 도우미가 없는 테스트 프로필이므로 앱의 기록 상태는 `review`(보안 확인 필요)다. 백신 검사가 성공한 것으로 처리하지 않았다. 전체 영상을 사람이 처음부터 끝까지 시청하거나 모든 프레임을 디코딩한 검사는 아니다. 921개 구간 수신, 전체 길이, 영상·음성 트랙, 처음·끝 디코딩을 확인했다.

사용자 PC의 로그인·재생 세션, Windows 10·11, 설치된 Chrome 버전, 실제 백신 도우미·Defender 검사는 별도 확인 대상이다. Cloudflare 인증을 우회하거나 해제한 결과라고 주장하지 않는다.

## 반영 및 게시 범위

사용자는 검증 브랜치 업로드와 Windows 러너 실행을 명시적으로 허용했다. 워크플로는 수동 실행·`contents: read` 권한이며, 등록된 `release-missav.yml` 경로도 이 브랜치에서만 읽기 전용 검증 내용으로 사용한다. 빌드 ZIP은 게시하지 않고 로그·검사 JSON·화면만 Actions 아티팩트에 7일 보관한다.

main, 기존 태그·릴리즈, 게시 환경은 변경하지 않는다. 수정은 검증 브랜치에만 반영한다.

실제 URL 검사에서도 상태 JSON과 로그만 보관했다. 영상과 프레임은 아티팩트에 올리지 않았으며, 확인 후 임시 브라우저 프로필과 다운로드 파일을 삭제했다. main은 `e64ac768438dac56fdb0e7df928042814bc69e98`, 최신 안정 릴리즈는 `v1.19.4`, 기존 미리보기는 `v1.20.1-preview.1`로 유지됨을 API로 확인했다.
