실행 가능한 검사: `npm run verify`. 실제 수행 결과의 시나리오와 빌드 해시는
`reports/browser.json`, 설치 구성은 `reports/build.json`에 있다. 기존 원본 전용
구현을 제거하면서 해당 구현에만 의존하던 과거 비교 테스트도 제거했고, 현재
로컬 엔진과 공통 구성요소의 검사를 유지/추가했다. 실패한 검사를 생략한 것은 아니다.

1.2.0 추가 검사에서 포함 FFmpeg 코어의 VP9 인코더가 메모리 접근 오류를 재현했다.
따라서 WebM 출력은 실제로 성공한 VP8/Opus로 제공하며 실패한 VP9 인코딩을 통과로
표기하지 않는다. AAC/Matroska 병합의 초기 코덱 지연을 제외하고 안정된 음성 구간의
주파수를 측정한다. 영상은 코덱 복사 스트림의 해시를 비교한다.

별도 `npm run test:http3`의 4개 검사는 임시 TLS/QUIC 서버와 폐기할 Chrome 프로필로
실제 HTTP/3 MP4·Range·HLS/Wasm 저장 및 인증서 검증을 수행한다. 결과는 `reports/http3.json`.
시험 브라우저만 루프백 QUIC 경로를 지정하며 제품은 Chrome 자동 협상을 사용한다.
제품의 실제 확장 설치/API 통합과 공개 사이트의 자동 협상 전체를 검증한 것은 아니다.

실서비스 사이트별 로그인·서명·지역·CDN 호환성, 모든 HLS/DASH 변형, 라이브/DRM,
원본의 모든 전용 기능은 동등성 보장 범위가 아니다. 지원 범위는 `LOCAL_MODE.ko.md` 참조.
검증용 입력/출력·화면은 `test-results`에 있으며 설치/소스 ZIP에 포함하지 않는다.

## 1.5.0 Windows 백신 자동 선택 검증

Windows 기본값은 Defender이며 활성 타사 백신은 Windows Security Center COM 정보와 AMSI 공급자 등록이 일치할 때 표준 인터페이스로 연결합니다. ClamAV의 단순 설치는 Windows 기본값을 바꾸지 않습니다. 명시적 `--scanner` 또는 `--clamav` 선택만 우선합니다. Defender는 기존 OS 보호 정책을 존중하고 활성 Normal 모드인지 확인합니다.

Windows 관련 네이티브 검사는 Windows 기본 선택·활성/비활성 타사 제품·미지원 공급자·불명확한 조회·결과·HRESULT·정리·파일 전체 버퍼·128MiB 제한을 포함합니다. Windows COM/AMSI/Defender 부분은 대역입니다. `reports/native-tests.json`은 호스트·Windows 모듈·설치 도구 해시를 기록하며 패키징 시 일치를 요구합니다. 실제 Windows 백신 제품별 연동은 이 Linux 환경에서 검증하지 않았습니다.

- 구조 감사는 런타임 모듈32개·진입점8개·전체 소스106개를 확인했다. 알고리즘 다섯 영역은 현재 소스 스냅샷에서 별도로 실행하여 통과했다. UI 비교의 역사적 원본 해시는 유지하며 내부 검사 요약 표시만 메모리에서 맞춰 전체 텍스트 동등성·행·초점·토큰·진행 버튼 검사를 보존한다. 이 벤치마크가 내부 검사 전체 성능을 측정하거나 모든 입력의 실행 시간을 보장하는 것은 아니다.
- 도우미 변경 뒤 실제 ClamAV1.4.6/시험용 서명 연동6개를 다시 실행했다. 시험 표식 원문·시험 파일·DB는 배포하지 않으며 빌드·패키지 단계에서 원문 표식 잔존을 검사한다. 현재 결과·배포 해시·로그 해시는 `release-validation.json`과 각 JSON 보고서를 기준으로 확인한다.
- 정적 검사는 보조 탐지이며 모든 바이러스·악성 미디어나 취약점 악용을 탐지하는 백신이 아니다. Chrome 직접 다운로드의 실제 디스크 파일을 읽으려면 새 도우미 설치가 필요하다. 브라우저256MiB·네이티브2GiB−1바이트 및 구조 예산, HLS 조각 경계의 한계는 `INTERNAL_SCAN.ko.md`에 있다. Windows 실기기·실제 확장 설치·기존 FFmpeg5.1.4의 잔여 위험은 기존과 같다.


## 1.12.1 백신 연동 ON/OFF 검증

- 최종 전체 검사는 단위 **257개**, Python 네이티브 **69개**, Chromium 하네스 **84개**를 통과했다. 새 UI의 실제 Chromium 세부 검사8개는 단위 합계에 포함하며 별도 합산하지 않는다. 팝업6·DB19·소유 입력 Worker8도 기존 브라우저 시나리오의 내부 항목이다.
- 기본 ON과 엄격한 boolean 설정, 내장 DB 허용 키·이전·저장, 일반 창 재열기와 시크릿 실행 메모리의 분리를 검사했다. 웹페이지·다른 확장·다른 모드 발신자와 잘못된 설정값은 거부한다. 저장 실패를 성공으로 표시하거나 미확인 설정을 OFF로 해석하지 않는다.
- OFF에서는 상태 확인·검사에 네이티브 포트를 열지 않고, 권한 조회 전과 대기열 진입 뒤에도 설정을 확인한다. 진행 중 포트는 종료하며 늦은 응답은 반영하지 않는다. 운영체제가 시작한 검사나 OS 실시간 보호를 종료하는 기능은 아니다.
- 실제 준비 바이트의 영상 다운로드가 OFF에서도 SHA-256 동일 파일로 저장되고 `disabled`로 완료되는지 확인했다. 이 상태는 백신 위협 미탐지가 아니며 자동 업스케일링을 제안하지 않는다. 외부 도우미의 응답이 로컬 전용 `disabled` 상태를 위조하지 못하는지도 검사한다.
- 내부 위험 신호·백신 위협·Chrome 경고는 계속 검토를 요구한다. 기존 백신 위협과 네이티브에서 막 확인한 해시/크기 연결 내부 위험 신호가 Chrome 경고 전환·OFF·Chrome 허용 순서에서도 보존되는지 검사했다. OFF에서 재검사로 이전 위협 기록을 지우지 않는다.
- 마지막 설정 조회가 오래된 ON을 반환하는 동안 OFF 또는 OFF→ON으로 바뀌는 두 경우에도 이전 작업의 자동 처리가 시작되지 않는다. 검사 연결과 확대 제안 모두 설정 세대를 확인하며 OFF는 진행 중 제안 세대를 철회한다.
- UI는 저장·복원 지연, 실패 후 재조회, 다른 창 변경, 오래된 조회 응답과 권한 응답을 검사한다. 연결 버튼은 최신 설정을 확인한 뒤 유효한 사용자 클릭에서만 선택 권한을 요청한다. OFF이면 권한 창을 요청하지 않고, 클릭 유효기간이 지났으면 재클릭을 안내한다. 수명주기 테스트는 한 번의 마이크로태스크 가정 대신 실제 요청 전송을 기다리며 정확한 시간 한도·중복 종료 검사를 유지한다.
- 구조 감사는 런타임 모듈33개·진입점8개·전체 소스109개를 확인했다. README에는 프로젝트의1.0.0~1.12.1 총15개 버전을 최신순 표로 정리했으며, 원본 확장10.6.1.2와 구분한다. 코드·보고서·ZIP은 최종 배포 해시를 기준으로 대조한다.
- Python 도우미 소스는1.12.0과 동일하다. 네이티브69개를 재실행했고 동일한 소스 해시에 연결된 실제 ClamAV 연동6개 근거를 유지한다. 공식 서명 최신성·실제 Windows API·관리자 정책으로 차단된 확장 설치 통합은 기존 검증 범위 밖이다. 내부 정적 검사가 완전한 백신이 아니라는 한계도 유지한다.

## 1.13.0 대용량·병렬·디스크 기반 다운로드 검증

- 전체 검사는 단위 **292개**, Python 네이티브 **69개**, Chromium 하네스 **89개**를 통과했다. 실제 HTTP/3 **4개**와 알고리즘 **5개 영역**은 별도 실행한다. 새 대용량 시나리오5개는 브라우저89개에 포함하며 중복 합산하지 않는다. 결과는 `large-download.json`, `release-validation.json`과 각 빌드 연결 보고서에 있다.
- 일반 파일은 안전한 전체 길이·강한 ETag·Range 응답이 있을 때 최대4개, 각4MiB 구간을 병렬로 받는다. 최종 URL·ETag·범위·길이가 다르면 실패하고 서로 다른 버전을 합치지 않는다. 안전한 분할 조건이 없으면 전체 응답을 한 번 순차 저장한다. 응답을 무시한 Range200 본문은 재사용하며, 확인용206에 식별자가 없으면 새 전체 요청을 사용한다.
- HLS/DASH 원본 저장은 조각을 최대4개 병렬로 받으며 Worker별1MiB 블록으로 단일 OPFS 컨테이너에 쓴다. 입력 가상 파일은 extent 목록으로 읽고 별도 출력 파일에 병합한다. 열린 동기 파일 핸들은2개로 유지하며, 같은 URL의 서로 다른 범위 응답은 일관된 강한 ETag를 요구한다. 실제 고정 FFmpeg 코어에서3GiB를 넘는 파일 오프셋 읽기·쓰기·탐색과 MP4 faststart·전체 디코드를 검사했다.
- 실제 Chromium은 **2,147,506,265바이트** MP4를 최대4개 Range로 받아 파일로 저장했다. 전체 SHA-256이 원본과 같고 트랙·길이·디코드가 일치한다. 같은 크기의 DASH 입력을 실제 보호된 디스크 Worker로 처리해 코덱 복사 스트림 해시·12프레임·음성·길이를 보존했다. 거대한 free box를 삽입한 소유 표본이며 결과 대용량 파일은 검사 뒤 삭제했다.
- 별도 실제 영상의 **14,402초** 타임스탬프와2프레임이 보존됐다. 긴 길이를 거부하지 않는지 확인하는 희소 프레임 표본으로, 연속4시간 영상의 처리 속도나 모든 길이·서버의 성공을 보장하지 않는다. 원본 다운로드의 미디어 용량·길이·전체 준비 시간 상한은 제거했지만 네트워크 유휴 시간 한도(일반 파일30초·스트림 조각60초)·재시도·유한 메타데이터100,000조각/8MiB 보호와 저장 공간 한도는 유지한다. MP3/M4A 변환·업스케일링·로컬 변환의 기존 별도 자원 한도도 유지한다.
- 취소와 명시적으로 주입한 QuotaExceeded 오류에서 형제 요청 종료·임시 파일 삭제를 확인했다. 일반 임시 창의 제한된 저장 모델 대신 폐기할 일반 Chromium 디스크 프로필을 사용하며, localhost 시험 origin에만 CDP8GiB 할당량을 지정했다. 시험 뒤 overrideActive=false 복원을 확인했다. 제품 권한·CSP·OS·사용자 프로필 변경은 없으며 실제 확장 `unlimitedStorage` 통합을 검증한 것은 아니다.
- 새 큰 파일 경로는4MiB씩 전체 SHA-256을 계산한다. 최종 파일256MiB 이하는 기존 전체 정적 검사를 유지하고 초과 파일은 앞8MiB 정적 검사만 수행해 범위 미완료를 기록한다. 조각 입력은 디코딩 전 중첩 블록으로 검사한다. 브라우저의 큰 Blob 전체 arrayBuffer 호출이 없도록8MiB 보호 장치를 두었지만 Worker 전체 힙/RSS를 측정한 것은 아니다. 네이티브 백신·AMSI의 기존 크기 한도를 넘으면 검사 완료로 표시하지 않는다.
- 구조 감사는 런타임 모듈38개·진입점9개·전체 소스119개와 미참조/순환0을 확인했다. 독립 검토자가 구현·정적 검사·취소·검증 범위와 빌드 연결을 교차 검토했다. Python 구현은 변경하지 않아 같은 소스 해시의 실제 ClamAV6개 근거를 유지하며 이번에 새로 실행했다고 표기하지 않는다. 설치된 Chrome API·Windows 백신·기존 FFmpeg5.1.4 잔여 위험이라는 한계는 유지한다.


## 1.14.0 빌드 경량화·주소 복사 최종 검증

- 최종 단위 **308개**, 네이티브 **69개**, Chromium 하네스 **90개**, 실제 HTTP/3 **4개**, 알고리즘 **5개 영역**을 통과했다. 팝업6·DB19·소유 입력 Worker8·새 주소 복사7개는 브라우저 시나리오의 내부 검사이며 합계에 다시 더하지 않는다. 전체 통합 실행은307개 단위·69개 네이티브·90개 브라우저를 통과했고, ZIP 압축 회귀1개를 추가한 뒤 최종 단위308개와 구조 감사·알고리즘도 다시 통과했다. 패키지 작성 코드만 바뀌었으므로 현재 런타임 빌드와 브라우저·HTTP/3 결과를 그대로 대조한다. 통과 결과·로그 해시는 `release-validation.json`을 기준으로 확인한다.
- 앱 ESM8개를 함께 빌드해 공유 모듈15개를 출력하며 콘텐츠 스크립트는 독립 IIFE다. 앱 JavaScript는 모든 진입점9개와 공유 모듈을 한 번씩 합산해 **288,971 → 171,634바이트(40.61% 감소)**다. 같은 PNG 두 개의 정확한 바이트와 manifest·HTML 별칭을 유지하고 UTF-8 문자열을 그대로 출력한다. 실제 esbuild 통합 표본은 동작·한글 문자열·진입점 namespace 비공개와 잘못된 공유 연결·원격 import·추가 export의 거부를 확인한다.
- 엔진은 Brotli quality11/window22 뒤 AES-256-GCM으로 포장한다. 압축 해제 모듈 경로·크기·해시도 인증 문맥에 연결하고 오프라인 해제 Wasm의 정확한 길이·SHA-256을 확인한 뒤 실행한다.64KiB 블록과 정확한 출력 길이, 잘림·추가 입력·정체·과대 출력·사전/진행 중 취소·메모리 정리를 검사했다. 기존 gzip 검사도 유지한다. 별도 실제 Chromium 표본에서32,232,419바이트의 고정 FFmpeg와 전체 SHA-256이 일치했고, 보호된 최종 빌드로 모든 영상·음성·변환·병합·확대 및2GiB 초과 다운로드를 다시 통과했다.
- 설치 ZIP·전체 배포 리소스에는 새 디코더와 필수 MIT/BSD 고지를 포함한다. 각 ZIP 멤버에 DEFLATE level9를 명시하며 실제 압축 바이트를 독립 zlib 오라클과 비교했다. 기존 작성기에서 실패하고 수정 후5개 ZIP의 내용·CRC·날짜·모드·별칭이 일치한다. 정확한 최종 바이트와 절감률은 `LIGHTWEIGHT_BUILD.ko.md`, `lightweight-build.json`에 있다. 압축으로 늘어난 빌드 시간·해제 메모리를 다운로드·인코딩 속도 향상으로 표현하지 않는다.
- 공식 저장소5개를 고정 리비전으로 비교하고 주소 복사를 독립 구현했다. 팝업·전체 앱의 새 권한 없는 실제 Chromium 컨텍스트에서 클릭 복사가 먼저 성공한 뒤 테스트 읽기 권한으로 URL을 대조한다. 키보드·합성 클릭 거부·수동 선택 창·초점 복원·최신 URL·비HTTP(S) 거부·옵션별 활성 기록 집합을 검사한다. 제품은 클립보드를 읽거나 자동 복사·외부 전송하지 않는다. Chrome 확장 API·의도적 복사 거부는 대역이라는 범위를 유지한다.
- 소스 구조는 앱 모듈39개·앱 진입점9개·벤더 진입점1개·소스123개다. `brotli-dec-wasm/web`의 정확한2.3.2 버전·npm 무결성·래퍼 기본 export·Wasm 정적 복사·경로 및 충돌을 별도로 감사하며 앱의 일반 외부 패키지 import를 허용하지 않는다. 앱 진입점 export0과 필요한 공유 내부 export를 구분한다. 권한·CSP·외부 연결 표면은 확장하지 않는다.
- 독립 검토자는 기능·빌드·압축 해제·고지·ZIP과 각 회귀 검사를 교차 검토했다. npm 공지는 고정 lockfile에서0건이며 Rust/Wasm·기존 FFmpeg5.1.4·운영체제 전체 취약점 검사가 아니다. Python 구현은 그대로여서 같은 소스 해시의 실제 ClamAV6개 근거를 유지한다. 실제 Chrome 확장 설치·Windows 백신·Chrome120 실기기 실행은 이번 환경에서 검증하지 않았다.

- 전체 단위308개·네이티브69개·브라우저90개를 통과했다. 빌드·팝업·큰 파일·HTTP/3 보고서는 최종 배포 해시로 대조하며, 소스 구조와 알고리즘5개 영역도 고정 소스로 검사한다. Python/백신 구현은 바꾸지 않았고 기존 실제 ClamAV6개 근거는 같은 소스 해시로 유지한다. 자세한 배치·화면과 수치는 `POPUP_COMPACT.ko.md`, `popup.json`, 최종 로그·해시는 `release-validation.json`에 있다.

## 1.15.0 저장 폴더와 자동 저장 검증

- 전체 단위 **309개**, 네이티브 **69개**, 브라우저 **91개**, 실제 HTTP/3 **4개**를 통과했다. 저장 폴더 **10개**, 팝업 **8개**, DB **19개**, 주소 복사 **7개**, 소유 입력 Worker **8개**, 큰 파일 **5개**는 브라우저 시나리오의 내부 검사이며 합계에 다시 더하지 않는다. 알고리즘 5개 영역은 최종 소스로 별도 검사하고 로그와 해시를 release-validation.json에 연결한다.
- 최초 확인 전에는 일반 파일·감지 미디어·직접 주소·재시도·단축키·변환 결과 저장을 시작하지 않는다. 중앙 확인 절차는 기록 생성·미디어 준비·전송 전에 적용한다. 사용자의 명시적 confirmed:true 확인만 저장하며 DB 읽기·커밋 오류에서는 확인되지 않은 상태로 처리한다. 시크릿 확인은 일반 DB와 분리한 실행 메모리다.
- 일반/스트림/오디오 다운로드와 미디어 도구의 결과 저장 모두 saveAs:false·conflictAction:uniquify를 적용한다. 준비한 변환 결과는 최초 설정 중 원래 탭에 남기며 저장 요청 중 결과가 바뀌면 이전 결과를 저장하지 않는다.
- 실제 절대경로는 Chrome 설정에서 선택한다. 앱에 적용되지 않는 절대경로 입력란이나 확인하지 못한 현재 경로를 표시하지 않는다. 매번 저장 위치 확인 OFF가 필요하고 다른 Chrome 다운로드에도 적용됨을 안내한다. 폴더 권한·조직 정책·Chrome 보호 확인은 우회하지 않는다.
- 2GiB 초과 병렬 일반 파일·DASH 디스크 병합, 취소/할당량 정리, 14,402초에 걸친 두 프레임의 유한 DASH 영상 검사를 다시 통과했다. 마지막 경우는 4시간 연속 영상의 처리량 시험을 뜻하지 않는다.
- Chrome API·미디어 준비의 새 폴더 검사는 명시적 대역이다. 보호된 배포 background/UI·DOM·IndexedDB는 실제 Chromium에서 실행한다. 관리자 정책으로 실제 확장 설치는 계속 차단되어 있으며, 실제 사용자 다운로드 경로/Chrome 옵션을 변경하지 않았다.
- GitHub Release 워크플로는 ZIP 버전·SHA-256·멤버 경로·CRC·태그의 정확한 커밋을 검사하고 설치 ZIP을 첨부한다. 다른 커밋의 기존 태그를 덮어쓰거나 저장소 공개 범위를 바꾸지 않는다. GitHub API 대역을 사용한 배포 검증은 실제 게시 성공 검증과 구분하며 실제 게시 실행은 main 푸시 후 GitHub Actions에서 수행한다.

상세 동작은 DOWNLOAD_FOLDER.ko.md, 세부 검사와 화면은 download-folder.json 및 test-results/download-folder-setup.png를 참고한다.

## 1.16.0 YouTube 지원 최종 검증

- 전체 단위 **344개**, 네이티브 **115개**, 보호된 배포 코드의 Chromium 시나리오 **92개**, 실제 HTTP/3 **4개**를 통과했다. YouTube 클라이언트15개와 Release19개는 단위344개에, 새 도우미46개는 네이티브115개에 포함된다. YouTube13개·최초 폴더10개·팝업8개·DB19개·주소 복사7개·소유 입력 Worker8개·큰 파일5개는 브라우저 시나리오 내부 검사이며 다시 더하지 않는다.
- YouTube의 H.264/AAC MP4, VP9/Opus WebM, H.264/Opus MKV, AV1/AAC MP4의 실제 병합과 영상·음성 인코딩 패킷 SHA-256 보존을 검사했다. MP3/M4A 변환은 실제 파일로 확인했다. 음성이 약속된 별도/통합 입력에 실제 음성 트랙이 없으면 영상만 성공 처리하지 않고 실패한다.
- 요청 ID·원본 영상 ID·HTTPS Googlevideo 주소·필드·UTF-8 바이트 예산을 검증하고 offscreen에서 다시 대조한다. UI 선택 전에는 추출하지 않으며 최초 폴더 설정·취소·만료 주소 재추출·서명 URL 미보관·백신 OFF 독립 동작·시크릿 DB 분리를 확인했다.
- 실제 고정 yt-dlp/EJS와 Deno를 사용한 별도 오프라인 검사 **8개**를 통과했다. 공식 SHA-256 wheel과 설치 파일·실행 파일의 바이트 일치를 확인했다. 시험 추출기를 명시적으로 주입했고 실제 EJS 프로토콜·Deno 파일/네트워크 권한 거부·실제 제공자의 jitless 적용도 확인했다. 실제 YouTube 사이트의 서명·PO 토큰·접속 성공을 검증한 결과는 아니다.
- 독립 검토에서 native stdin EOF 감시의 Python 종료 충돌, Deno 실행 경로 신뢰 재확인, 응답 규격 불일치, 음성 누락 가능성을 발견해 수정했다. 실제 열려 있는 stdin 파이프·자손 프로세스 종료 회귀 검사와 원본 음성 필수 매핑 검사를 유지한다. 실제 패키지 제공자를 확인해 JIT 제한 설정 키도 youtube-ejs로 수정하고 별도 검사로 확인했다. 마지막 native 수정 후115개를 다시 통과했다.
- YouTube 도우미 ZIP은 정확한4개 소스·설치·요구사항·안내 파일만 포함한다. AV 도우미 ZIP은 기존5개 파일로 분리한다. 두 도우미 모두 사용자 설정·venv·계정·캐시·테스트 미디어·실행 바이너리를 넣지 않는다. 소스 ZIP에서도 private config·가상환경·인증 파일을 제외하며 누락된 도우미 파일과 오래된 성공 체크섬을 허용하지 않는다.
- Release 워크플로는 확장·YouTube 도우미 ZIP을 함께 첨부한다. 실제 ZIP과 모의 API를 사용하는19개 검사에서 체크섬·멤버 경로·CRC·원본 바이트·고정 태그 커밋·실패 처리를 확인했다. 실제 게시 성공은 최종 main 업로드 후 별도 확인한다.
- 실제 unpacked 확장 설치와 Chrome native 등록은 클라우드 관리자 정책으로 검증하지 못했다. 실제 Windows Job Object·레지스트리 API와 live YouTube 접근은 이 Linux 환경에서 실행하지 않았다. 네트워크 제한을 우회하지 않았으며 실제 공개 영상에서의 추가 확인이 필요하다.
