# 알고리즘 조사·최적화 · My Video App 1.8.0

조사 기준일은 **2026년 10월 19일(한국 시간)**입니다. 1.7.0의 `6983b53`을 기준으로 현재 소스의 복잡도·할당·반복 작업을 분석하고, 관련 공식 문서와 소스 13개를 HTTPS로 직접 확인했습니다. 접근 가능한 공식 자료를 대상으로 한 구현 중심 조사이며, 이 날짜까지 발표된 모든 논문을 전수 조사했다는 뜻은 아닙니다. 조회 URL·시각·내용 해시는 `algorithm-research.json`에 있습니다.

## O(n)보다 효율적인 직접 구현이 가능한 범위

입력 전체를 처리하는 작업과, 이미 처리한 입력에서 반복 조회하는 작업은 하한이 다릅니다.

| 작업과 n의 의미 | 하한·개선 가능성 |
| --- | --- |
| B바이트를 정확히 저장·해시·검사 | 임의의 마지막 바이트도 결과에 영향을 주므로 최악에는 Ω(B) 읽기·쓰기가 필요합니다. 검사를 생략하는 근사·표본 검사로 대체하지 않습니다. |
| P개 출력 픽셀과 F개 프레임의 확대 결과 생성 | 결과 전체를 실제로 생성하려면 Ω(P×F)가 필요합니다. GPU·SIMD·병렬화는 처리량을 높일 수 있지만 이 출력량 하한을 없애지 않습니다. |
| 순서가 정해지지 않은 V개 후보 중 최선 하나 선택 | 마지막 후보가 최선일 수 있으므로 Ω(V) 확인이 필요합니다. 전체 정렬 대신 선형 선택으로 Θ(V)에 도달할 수 있습니다. |
| 이미 색인한 N개 미디어의 ID 반복 조회 | 처음 색인을 만드는 Ω(N) 작업과 O(N) 추가 저장 공간을 지불하면 해시 기반 구현에서 조회가 기대 O(1)이 됩니다. JavaScript Map 규격은 평균적으로 선형 미만 접근을 요구하며 최악 O(1)을 보장하지 않습니다. |
| 변화가 없는 화면이나 관련 없는 페이지 변경 | 직전 상태·변경 기록을 사용해 불필요한 DOM 재생성을 피할 수 있습니다. 전체 상태 응답이나 관련 DOM을 실제로 읽는 비용까지 O(1)이 되는 것은 아닙니다. |
| 이미 독립 버퍼에 있는 B바이트의 작업자 전달 | 소유권 이전으로 추가 B바이트 복사를 제거할 수 있습니다. 파일 읽기·인코딩·FS.readFile까지 O(1)이 되는 것은 아닙니다. |

이 프로젝트에 맞는 색인·안정적인 선형 선택·메모리 소유권 처리·변경 필터를 직접 구현합니다. 새로운 범용 이론 알고리즘을 발명했다고 주장하지 않습니다. 사전 처리·메모리·수정 시 무효화 비용을 포함해 판단합니다.

## 적용 내용과 측정

수정 담당과 독립 검토 담당이 기존 결과·예외·보안 한도를 비교했습니다. `npm run bench:algorithms`는 다섯 영역을 순차 실행하고 시작·종료 때 소스 64개 해시가 같은지 확인했습니다. 환경은 Node 24.19.0, Linux x64, AMD EPYC 9V74, Chromium 154입니다. CPU는 실행 환경에 노출된 5개 논리 CPU이며 전용 장비의 보장 성능을 뜻하지 않습니다.

| 적용 경로 | 복잡도·할당 변화 | 이번 통합 실측 |
| --- | --- | --- |
| 유한한 화질 메타데이터의 최선 한 개 선택 | 비교 정렬 경로 O(V log V)·임시 O(V) → Θ(V)·추가 O(1). 동점 순서 유지. 비정상 수치의 비교 그룹은 기존 정렬 대체 경로를 사용하므로 전체 최악 경로가 선형으로 바뀐 것은 아님 | 후보 8/64/1,024/4,096개에서 해당 선택 구간 약 6.03/8.89/21.26/27.06배. 4,096개는 1.611 → 0.0595ms |
| HLS 기본 오디오·DASH 오디오 선택 | 정렬 대신 순차 선택. 첫 기본 항목·동점·잘못된 수치 결과 보존 | 실제 HLS/DASH 저장과 오라클·생성 입력 비교로 동등성 검사. 별도 오디오 선택의 속도 배수는 주장하지 않음 |

| 무시된 Range 응답의 결과 조립 | B 전체를 합친 뒤 R을 다시 복사하던 O(B+R) → 조각 위치와 범위만 조립 O(C+R). 전체 B 읽기·검사는 유지 | 64MiB 응답에서 1MiB를 추출할 때 새 복사·backing buffer 65MiB → 1MiB, 조립 구간 중앙값 23.42 → 0.140ms |
| 전체 응답 조립 | 다중 조각은 O(B)·B 복사 유지. 정확한 독립 단일 버퍼는 추가 복사 O(1) | 다중 8MiB는 1.48 → 1.45ms로 실질적인 가속 주장 없음. 단일 8MiB는 추가 8MiB 복사 제거 |

| 미디어와 무관한 변경 | 대기 발견·기준 URL·제목·MIME 등 관련 상태를 확인한 뒤 불필요한 전체 검색 생략. 관련 변경은 여전히 전체 검색 | 링크 1만 개와 무관한 변경 100회·리소스 관측 1,000개에서 검색 200 → 0회. 합성 배치 경과 10,993.7 → 5.1ms |
| 변경 없는 UI 400행의 갱신 100회 | 전체 응답·서명 비교는 선형으로 유지. 같은 행의 DOM 재생성만 생략 | 생성 요소 240,000 → 0개, 목록 노드 변경 80,000 → 0회. 배치 786.4 → 82.3ms |
| 진행률 한 행만 바뀌는 UI 갱신 100회 | 변경된 행만 새로 만들고 나머지 행·초점을 유지 | 생성 요소 240,000 → 600개, 목록 노드 변경 80,000 → 200회. 배치 772.1 → 83.1ms |
| 메시지 검증 예산 | 한도를 넘는 예정 노드는 자식 튜플·값 읽기 전에 거부. Object.keys의 O(width) 시간·공간은 남음 | 50만 항목 거부 중앙값 29.20 → 12.48ms, 독립 프로세스 최대 RSS 190,428 → 82,588KiB. 정상 6,001노드는 0.351 → 0.337ms |

선택·조회·조립·전달은 워밍업 후 교차 순서로 여러 번 측정한 중앙값입니다. 보안 검증은 독립 프로세스에서 반복 측정한 중앙값과 범위입니다. **UI·수집기는 100회/20회 작업 배치 한 번의 경과 시간이므로 중앙값이 아닙니다.** 수집기의 PerformanceObserver·500ms 디바운스 시계와 UI의 확장 API는 명시적인 대역입니다. 해당 비교의 실제 DOM·MutationObserver·Chromium 실행을 확인했으며, 구조적인 검색·생성·변경 횟수 감소를 우선 근거로 삼습니다.

버퍼 할당량은 코드가 실제로 만드는 데이터 버퍼의 크기를 센 값이며 전체 프로세스 최대 RSS와 같지 않습니다. 원본 입력 조각, File/Blob, 디코더, Wasm, 출력 메모리와 시스템 캐시는 별도입니다.

회귀 검사는 안정 정렬 오라클과 무작위·경계 입력, 원본 배열 순서, 요청 범위의 전체 용량 예약·취소, 색인 교체·퇴출·탭 종료를 검사합니다. 실제 Chromium Worker 8회에서 기존 복사와 입력 소유권 방식의 영상·음성·이미지·병합 출력 SHA-256과 전체 메타데이터가 같았고 원본 File 해시·랜덤 위치 읽기도 유지됐습니다. 수집기는 301개 발견 대기, base 추가·변경·제거, SPA 기준 URL, 제목 문자 데이터, source MIME·삭제, 불투명 주소 HTTP/3 관측을 비교합니다. UI는 초점·행 순서·삭제·중복 ID·새 보안 토큰·진행 중 버튼 상태를 검사합니다.

현재 측정값은 `performance.json`과 `performance-{state,media,transfer,ui,security}.json`에 있습니다. 각 표본과 단위·분산/범위·제외 조건을 함께 기록합니다. `tests/baselines`의 고정·해시 확인 기준 소스를 제공하므로 소스 ZIP에서도 Git 이력 없이 실행할 수 있습니다. 패키징은 소스 목록·각 파일 해시·하위 측정 보고서 해시가 달라지면 중단합니다.

측정 시간은 해당 연산의 범위에 한정합니다. CPU 선택·조회·버퍼 조립·DOM 갱신의 속도 배수를 전체 영상 다운로드·인코딩 배수로 해석하지 않습니다. 클라우드 CPU 부하, JIT, GC, 파일 캐시, 브라우저 스케줄링 때문에 절대 시간은 달라질 수 있습니다. 불안정한 시간 임계값으로 검사를 억지로 통과시키지 않고 결과 동등성과 작업량 감소를 별도로 확인합니다.

## 조사한 대안과 선택 기준

| 대안 | 판단 |
| --- | --- |
| 전체 정렬, 힙, Quickselect, 선형 최대 선택 | 최선 하나만 필요하므로 힙·Quickselect보다 단순한 선형 선택이 적합합니다. 동점은 기존 첫 항목을 유지하며 NaN/Infinity로 비교 순서가 불명확한 메타데이터는 기존 정렬 경로를 보존합니다. |
| Map 색인·영속 기록 캐시 | 메모리 안의 미디어 ID 색인은 반복 검색을 줄일 수 있습니다. 보안 결정의 영속 기록·Chrome 최신 상태까지 캐시해 재검사를 생략하지 않습니다. 기록 200개·복사 큐 4개·준비 큐 8개의 작은 정렬·검색은 별도 구조의 유지 비용을 함께 고려합니다. |
| ArrayBuffer 소유권 이전 | MDN은 ArrayBuffer 전달이 메모리 소유권을 옮기는 작업임을 설명합니다. 핀된 FFmpeg 코어의 FS.readFile이 독립 버퍼를 만드는지도 실제로 확인해야 하며, Wasm 힙·공유 버퍼·부분 뷰를 무조건 떼어 내면 안 됩니다. |
| HTTP Range 실패 시 부분 뷰만 반환 | subarray는 큰 원본 backing buffer를 계속 보유합니다. 정확한 범위 크기의 독립 버퍼를 만드는 방식과 비교합니다. 서버의 전체 응답 검사·용량 예약·취소·재시도 규칙을 유지합니다. |
| MutationObserver 기반 부분 작업 | 표준 변경 기록으로 관련 없는 이벤트를 거를 수 있습니다. 기준 URL·제목·소스·초기 수집 한도 뒤의 대기 항목은 놓치지 않아야 하므로 관련 변경은 기존 전체 스캔을 유지합니다. |
| FFmpeg Wasm 멀티스레드·SIMD | 상수 계수·병렬 처리량 개선 후보입니다. 공식 성능 페이지의 약 2배 수치는 오래된 core 0.12.3·Chrome 116 시험이며 이 앱의 실측이 아닙니다. CPU·메모리 증가, 추가 격리/호환 조건과 출력 재현성을 검증하지 않고 코어를 교체하지 않습니다. |
| WebCodecs·WebGPU | 하드웨어와 브라우저의 코덱·GPU 지원에 의존합니다. 디먹싱·먹싱·CPU 대체 경로와 수치/인코더 출력 차이도 다뤄야 하므로 동일 결과를 보장하는 즉시 교체 경로로 간주하지 않습니다. |
| Real-ESRGAN 등 학습 기반 초해상도 | 별도 모델·추론 자원이 필요하고 픽셀 결과가 기존 Lanczos와 다릅니다. 공식 구현도 타일별 처리의 결과 차이를 설명합니다. 기존과 같은 결과라는 조건을 유지하는 최적화에 섞지 않습니다. |
| 스트리밍 SHA-256·트리 해시 | WebCrypto digest는 스트리밍 입력을 지원하지 않습니다. 다른 해시·표본 검사로 바꾸면 기존 파일 신원 계약이 깨집니다. 원본 재해시와 백신 결과의 바이트 바인딩을 유지합니다. |
| Emscripten WORKERFS | 현재 핀된 코어의 지원과 실제 Chromium 출력·랜덤 읽기 호환성을 확인했습니다. 그러나 FileReaderSync 기반 읽기에서 작업별 처리 시간이 혼재되어 자동 적용하지 않았습니다. 기존 MEMFS에 새 입력 버퍼 소유권을 넘기는 작은 변경을 선택했습니다. |

네이티브 백신의 임시 파일 복사 방식도 두 번의 SHA-256·파일 신원 검증을 유지한 시제품과 비교했습니다. 64MiB 워밍 캐시 입력의 중앙값이 108.85 → 109.38ms로 개선이 없어 적용하지 않았습니다. 원본 읽기 128MiB·임시 쓰기 64MiB가 그대로 필요했고 실제 백신 시간은 이 실험에서 제외했습니다. Windows AMSI는 이미 bytearray·readinto·ctypes.from_buffer를 사용하므로 추가 전체 복사를 새로 제거한 것으로 주장하지 않습니다.

## 검토·검증 범위

`audit_media`, `audit_lifecycle`, `audit_native`, `audit_ui_package`, `algorithm_worker`가 담당별 분석·수정·동등성·성능 검증을 수행하고 `audit_approval`이 범위·실측 방법·최종 변경을 독립 검토합니다. 주 에이전트는 공식 자료 조사·통합 검사·보고서·배포물을 담당합니다.

실제 Chrome 확장 설치는 관리 정책으로 차단되어 확장 API는 브라우저 하네스의 대역으로 검증합니다. Windows 백신 API도 Linux에서는 대역이며 실환경 연동을 검증했다고 주장하지 않습니다. 미디어 처리·Wasm·브라우저 DOM·파일 출력 및 별도 ClamAV·HTTP/3 시험은 실제 실행한 범위를 기록합니다.


## 통합 실행 결과

엄격한 타입 검사와 빌드를 포함해 단위 104개·네이티브 48개·Chromium 하네스 72개·실제 ClamAV 6개·실제 HTTP/3 4개, 합계 **234개**가 통과했습니다. 실패·생략은 0개이며 알고리즘 벤치마크 다섯 영역도 별도로 통과했습니다. 각 생성 입력 비교나 Worker 실행 횟수를 합계에 다시 더하지 않았습니다. 현재 결과·빌드 해시·성능 보고서 해시와 한계는 `algorithm-validation.json`에 기록했습니다.

소스를 임시로 하나 추가한 상태에서 실제 패키징 명령이 소스 목록 불일치를 거부하고 기존 배포 체크섬을 변경하지 않는 것도 확인했습니다. 임시 파일은 즉시 제거했습니다.

설치 ZIP 24개·소스 ZIP 107개·도우미 ZIP 4개 파일이 현재 파일과 바이트 단위로 일치합니다. 다섯 ZIP의 CRC·경로·SHA256SUMS와 두 호환 별칭의 바이트 일치를 확인했습니다. 메일·캐시·키 파일·생성 빌드·검증 출력은 소스 ZIP에서 제외합니다.

실제 소스 ZIP을 임시 디렉터리에 풀고 `.git`이 없는 상태에서 다섯 벤치마크 영역을 다시 실행해 통과했습니다. 이 재현성 검사에서는 기존에 설치한 의존성 폴더를 임시 심볼릭 링크로 연결했으며 새 환경의 의존성 설치까지 검증했다고 주장하지 않습니다. 임시 디렉터리는 검사 후 제거했습니다.

최종 독립 기술 판정: **APPROVE — My Video App 1.8.0**. `audit_approval`이 현재 코드·복잡도·측정 방법·234개 검사·5개 벤치마크 영역과 다섯 ZIP을 별도로 확인하고 커밋·업로드를 막는 미해결 문제가 없다고 승인했습니다.
